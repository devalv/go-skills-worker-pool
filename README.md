# go-skills-worker-pool

Локальная in-memory очередь фоновых задач на Go с ограничением параллелизма,
дженериками, статусами и хранением результатов по TTL. Без внешних зависимостей.

```text
simple/
  pool.go
  pool_test.go
examples/simple/
  main.go
Makefile
```

## Использование

```go
import (
    "context"
    "time"

    "github.com/devalv/go-skills-worker-pool/simple"
)

type VM struct { ID string }

func newPool() (*simple.Pool[any], error) {
    return simple.New[any](simple.Config{
        Workers:       4,
        QueueCapacity: 100,
        Retention:     time.Hour,
        TaskTimeout:   10 * time.Minute,
    })
}

func submit(pool *simple.Pool[any]) (simple.ID, error) {
    return pool.Submit(func(ctx context.Context) (any, error) {
        // Здесь можно вызвать API и дождаться завершения внешней операции.
        return VM{ID: "vm-demo"}, nil
    })
}

func checkService(pool *simple.Pool[any]) (simple.ID, error) {
    return pool.Submit(func(ctx context.Context) (any, error) {
        // Другая операция с другим типом результата в том же пуле.
        return true, nil
    })
}

func stop(pool *simple.Pool[any]) error {
    ctx, cancel := context.WithTimeout(context.Background(), 30 * time.Second)
    defer cancel()
    return pool.Shutdown(ctx)
}
```

Полный запускаемый пример с созданием VM и проверкой сервиса: `make run-simple`.

В очередь передаётся функция, а горутину запускает сам пул. Не запускайте работу через
`go` внутри переданной функции: её возврат означает завершение задачи и освобождает
слот воркера. Отдельная горутина продолжила бы работу вне ограничений пула.

При `Pool[any]` результат сохраняет свой конкретный тип. После `Get` и проверки
`succeeded` используйте проверку типа, например `vm, ok := task.Result.(VM)`.
`func(context.Context) (VM, error)` нужно обернуть в функцию с результатом `any`,
как в примере: Go не преобразует такие типы функций автоматически.

## Контракт

- `New[R](config)` запускает воркеры. `R` — тип результата, общий для пула.
  Для разнородных результатов используйте `New[any]`, для одного типа — например,
  `New[VM]`. Число воркеров и ёмкость очереди должны быть положительными;
  длительности — неотрицательными.
- `Submit(func(context.Context) (R, error))` ставит функцию в очередь и сразу
  возвращает ID принятой задачи. Аргументы конкретной операции захватываются замыканием.
  Функция вызывается воркером, когда он освободится. `nil` возвращает `ErrNilHandler`. При заполнении очереди
  возвращает `ErrQueueFull`, после начала остановки — `ErrClosed`. При ошибке ID равен нулю.
  Ёмкость ограничивает ожидающие задачи; одновременно выполняющихся не больше `Workers`.
- `Get(id)` возвращает снимок `Task[R]`: статус, результат, ошибку и время постановки,
  начала и завершения. Для неизвестной или истёкшей задачи возвращает `ErrNotFound`.
- Статусы: `queued` → `running` → `succeeded`, `failed` или `canceled`.
  Результат и ошибка окончательны только после завершения. Ошибка отмены контекста
  или дедлайна даёт `canceled`, прочая ошибка — `failed`. Паника обработчика
  преобразуется в ошибку с `ErrPanic`; воркер продолжает работу.
- `Retention` отсчитывается от завершения. Ноль отключает удаление результатов.
  Просроченные результаты недоступны сразу; фоновая очистка работает с интервалом
  `min(Retention, time.Minute)`. Ожидающие и выполняющиеся задачи не удаляются по TTL.
- `TaskTimeout` начинается при получении задачи воркером. Ноль отключает таймаут.
  Воркер освобождается только после возврата обработчика: Go не позволяет принудительно
  остановить произвольный код. Обработчик должен учитывать свой контекст и возвращать
  ошибку отмены. Успешный возврат считается успехом, даже если контекст уже отменён.
- `Shutdown(ctx)` прекращает приём и ждёт выполнения всех принятых задач.
  Если контекст истёк, метод отменяет контексты обработчиков и возвращает `ctx.Err()`.
  Оставшиеся задачи получают `canceled` по мере обработки воркерами, без вызова обработчика.
  Повторные и конкурентные вызовы безопасны; повторный вызов может дождаться завершения.
  Нельзя вызывать `Shutdown` из обработчика этого же пула: он будет ждать сам себя.
- После завершения `Shutdown` чтение результатов доступно, TTL проверяется при `Get`.
  Фоновая очистка завершается вместе с пулом; чтобы освободить всю оставшуюся память,
  нужно перестать хранить ссылки на пул.

## Интеграция с внешним API

Все задачи выполняются в фоне. Вызывающее приложение может
вернуть ID своему клиенту или опрашивать `Get` до конечного статуса. Контекст
HTTP-запроса не управляет временем жизни принятой задачи.

Обработчик определяет, что означает выполнение. Для синхронного API он возвращает
его результат; для асинхронного — запускает операцию и опрашивает её до завершения,
если результатом задачи должна быть готовая VM. Если обработчик возвращает только
ID внешней операции, `succeeded` означает успешный запуск этой операции.
Ожидание внешнего API занимает слот воркера, включая интервалы между опросами.

Каждый экземпляр пула имеет собственную очередь, ID и результаты. Нет обмена
между репликами, сохранения на диск или автоматических повторов. ID уникален
только внутри экземпляра пула и не подходит для поиска между репликами/перезапусками.
Сетевая ошибка не доказывает, что внешняя операция не выполнилась; повторное создание
ресурсов требует идемпотентности или проверки состояния во внешнем сервисе.

Данные, захваченные замыканием, и результаты с указателями, map или slice не копируются глубоко.
Не изменяйте их конкурентно без собственной синхронизации. TTL ограничивает время
хранения, но не число и объём результатов: под высокой нагрузкой память зависит
от частоты завершения, размера результата и выбранного TTL.
